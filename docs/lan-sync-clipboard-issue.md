# 局域网剪贴板同步：粘贴内容错乱问题总结

> 状态：时间戳同步已实现并部署到两台测试机，尚未提交；微信输入法的干扰无法在 EcoPaste 内彻底消除，见「现有结论」。

## 1. 背景

- 项目：EcoPaste（Tauri v2，Rust-First 剪贴板管理器），分支 `feat/lan-clipboard-sync`。
- 功能：局域网剪贴板同步（mDNS 发现 + SPAKE2 配对 + 加密 TCP）。文本、图片直接传；文件只传清单，对端粘贴时再按需拉取（接收侧用虚拟文件 `IDataObject`）。
- 测试环境：两台 Windows 电脑，本机 mechrevo（10.36.88.194）和 ThinkBook（10.36.90.98），都装了微信输入法（WeType 3.0.3.8）。

## 2. 用户报告的现象

1. 开启 EcoPaste 后，按 Ctrl+V 无效。
2. 本机先复制 A、再复制 B，在另一台机器粘贴出 B 之后，回到本机粘贴出来的是 A。

## 3. 已定位并修复的问题（提交 `4e893f8`）

| 问题 | 原因 | 处理 |
| --- | --- | --- |
| 同一次变更被处理两次 | 剪贴板事件监听和 700 ms 序号轮询都会捕获同一次变更 | 5 秒内相同内容哈希只处理一次 |
| 旧内容覆盖新内容 | 收到的远端内容写剪贴板失败时会退避重试，旧内容的重试可能晚于新复制落地；`write_to_clipboard` 内部还有一层不可中断的 8×200 ms 重试 | 写入前领取序号，被更新的内容顶替则放弃；同步写入改为单次尝试 `write_to_clipboard_once`，由外层统一重试 |
| 文件同步来回弹跳 | 收到的文件在本机是纯虚拟文件剪贴板；微信输入法会把它另存为临时 PNG 并放回剪贴板，EcoPaste 把它当成新复制再广播回去 | 按文件大小集合识别 120 秒内的回显，不再广播 |

## 4. 本次新增：时间戳同步（未提交）

思路：谁的时间戳最新，就同步谁的内容。

- **时间戳：** 混合逻辑时钟。本机复制取 `max(系统毫秒时间, 已知最新 + 1)`，因此看过对端内容之后的复制一定更新。
- **协议：** `ClipText`、`ImageStart`、`ClipFiles` 增加 `ts` 字段，`PROTOCOL_VERSION` 由 2 升到 3（旧版本互相发现不了，两台必须同时升级）。
- **接收规则：** 只有 `ts` 大于本机已知最新时才写剪贴板，同时登记为新的最新。更旧的文本、图片只进历史、不写剪贴板；更旧的文件清单直接丢弃。图片在 `ImageEnd` 到达时按 `ImageStart` 带来的 `ts` 判定。
- **时钟保护：** 对端时间戳超前本机超过 10 分钟的，按 10 分钟截断。
- **其它：** 云端同步仍沿用本机领取新时间戳的方式，不带对端时间戳；回显抑制和 5 秒去重保留。
- **主要改动文件：** `sync/apply.rs`、`sync/manager.rs`、`sync/protocol.rs`、`sync/mod.rs`、`sync/remote_files/mod.rs`、`clipboard/watcher.rs`。
- **检查：** `clippy -D warnings` 无警告；206 个单元测试通过；4 个局域网同步端到端测试和 1 个云端测试通过。

## 5. 根因调查（已定位）

### 对照实验

用独立探针（Win32 写入、PowerShell 写入、Win32 全格式读取、OLE 读取、前台窗口探测）加 EcoPaste 采集开关逐项消融，探针只用序号和剪贴板所有者记录微信输入法（`wetype_server`）的写入。两次复制间隔 400 ms，每组 6–12 轮：

| 条件 | 微信输入法写剪贴板的轮数 |
| --- | --- |
| 本机同步开启，对端 EcoPaste 在线 | 6/6、8/8、10/10 |
| 本机同步开启，对端 EcoPaste 停止 | 0/10 |
| 本机同步关闭 | 0/26 |
| EcoPaste 停止，探针自己做全格式读取 | 0/12 |
| 探针做 OLE 读取、`Clipboard.GetText`、前台窗口探测 | 各 0/6 |
| 复制间隔 1000 ms | 基本为 0（偶发 1 次，Win32 写入方的底噪） |

### 机制

微信输入法有跨设备剪贴板同步：本机复制 A、B，对端 EcoPaste 收到并写入后，微信输入法把这些内容经云端推回本机，约 1.2 秒后按序重放 A、B，写入方是 `wetype_server`。EcoPaste 把重放当成新复制：入库、打上最新时间戳、再广播给对端。对端写入后微信输入法又重放，A、B 在两台机器间交替互相覆盖，最终停在哪条取决于时序。

要点：
- 触发条件是"对端 EcoPaste 写入了内容"，和 EcoPaste 的读取方式无关；时间戳无法区分重放与真实复制。
- 此前的 Ctrl+V 无响应可能另有原因：一次实验中剪贴板被占用且序号不变，停掉 EcoPaste 后恢复，但后来发现当时屏幕已锁定，无法区分。

## 6. 修复（未提交）

- 在监听里加两步：每条真实捕获的内容登记进"近期内容"（15 秒，远端写入的内容也登记）；之后若剪贴板写入方是 `wetype_server` 且内容在近期内容里，判定为输入法重放，不入库、不打时间戳、不广播。
- 需要的新接口：`clipboard::clipboard_owner_exe()`（Windows 用 `GetClipboardOwner` 取写入方可执行文件名，macOS 返回 `None`），`sync::remember_content` / `sync::is_recent_content`。
- 取舍：用户在 15 秒内用微信输入法历史重新选取刚复制过的内容，不会作为新复制广播（剪贴板里仍是那条内容，本机可正常粘贴）。

## 7. 验证

- 单元测试 206 个通过，`clippy -D warnings` 无警告。
- 修复后本机 30 轮探针（间隔 100/400/1000 ms）：每轮只记录一次真实的 A、B，微信输入法的重放全部被忽略，本机没有再收到对端回传。
- 双机端到端（间隔 400 ms，两个方向各 6 轮）：本机→ThinkBook 6/6 两端都是 B；ThinkBook→本机 5/6，另一轮两端一致停在 X，ThinkBook 日志显示 Y 从未出现在它的剪贴板上，判断是测试脚本第二次写入失败，不是同步问题。
- 未验证：文件回显场景的真机验收；微信输入法"文件转临时 PNG"的路径目前仍只有单元测试。
